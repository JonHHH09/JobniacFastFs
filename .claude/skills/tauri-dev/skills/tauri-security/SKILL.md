# Tauri Security

These instructions and the files in `references/` are local copies of the official Tauri v2 docs (https://v2.tauri.app/security/, tauri-docs 4b74da6, 2026-10-13). Work only from them: before writing code or giving advice, read the reference file(s) for the task; cite the page URL from the file's Source header. If the references don't cover something, say so and point to the live page instead of filling the gap from memory.

## Project context
- App capability file: `src-tauri/capabilities/default.json`; all files in `src-tauri/capabilities` are enabled automatically unless `app.security.capabilities` is set in `tauri.conf.json` (capabilities.md).
- `src-tauri/tauri.conf.json` currently has `"app": {"security": {"csp": null}}`, so no CSP protection is active (csp.md: CSP is only enabled if set in the config).
- The app uses tauri-plugin-opener: its permissions must be referenced from a capability to be usable from the frontend (permissions.md). For the exact opener identifiers, see the tauri-official-plugins skill.
- Frontend is React + Vite on Windows; dev-server headers go in `vite.config.ts` (http-headers.md).

## Key rules
- Rust/plugin code has full system access; webview code only reaches resources through the IPC layer, restricted by capabilities, with scopes enforced by each command (overview.md).
- A capability grants or denies permissions to windows/webviews; a permission must be referenced in a capability to apply (capabilities.md, permissions.md).
- Windows/webviews in several capabilities get the merged permissions of all of them (capabilities.md).
- Boundaries depend on window labels, not titles; expose window creation only to higher-privileged windows (capabilities.md).
- Capability files: JSON or TOML in `src-tauri/capabilities`; reference by identifier in `app.security.capabilities` or inline objects, and the two can be mixed. Once capabilities are listed explicitly, only those are used in the build (capabilities.md).
- Capability fields shown in the docs: `identifier`, `description`, `windows`, `permissions`, `platforms` (`linux`, `macOS`, `windows`, `iOS`, `android`), `remote.urls` (capabilities.md).
- Set `$schema` to `../gen/schemas/desktop-schema.json` or `../gen/schemas/mobile-schema.json` (generated by tauri-build) for IDE autocompletion (capabilities.md).
- By default every command registered with `invoke_handler` is allowed for all windows/webviews; to restrict, use `tauri_build::AppManifest::new().commands(&[...])` in `build.rs` (capabilities.md).
- By default the API is only accessible to bundled code; remote sources need `remote.urls` in a capability. On Linux and Android Tauri cannot tell an embedded `<iframe>` from the window itself (capabilities.md).
- Capabilities do NOT protect against malicious/insecure Rust code, lax scopes, wrong scope checks in commands, WebView 0-days, or supply chain attacks (capabilities.md).
- Permission identifier forms: `<name>:default` and `<name>:<command-name>`; `<name>` is the plugin crate name without `tauri-plugin-`, not needed for app permissions (permissions.md).
- permissions.md says identifiers are `[a-z]` only with max length 116; plugins.md says lowercase letters, digits and hyphens (not leading/trailing), one colon, base max 64, full max 129. They disagree; check the live page if it matters (permissions.md, plugins.md).
- App developers may write capabilities in json/json5/toml, but permissions only in `toml` (in `src-tauri/permissions/`) (permissions.md).
- Permissions can allow/deny commands (`commands.allow`/`commands.deny`), define scopes, or both; `[[set]]` groups permissions under a new identifier (permissions.md).
- The `default` permission is added to the app config automatically when plugins are added via the Tauri CLI (permissions.md).
- Scopes: `allow` and `deny`; `deny` always wins over `allow` (scope.md).
- Scope types are plugin-specific serde types; the command itself must enforce the scope, so scope validation must be audited for bypasses (scope.md).
- Scopes apply to all commands via the plugin's global scope, or to selected commands when combined with an enabled command in a permission or set (scope.md).
- Runtime authority: on every invoke it checks that the origin is allowed for the command, injects applicable scopes, and otherwise denies the request so the command never runs (runtime-authority.md).
- CSP only applies if set in the config; make it as restrictive as possible and trust only hosts you own. Tauri appends nonces/hashes to bundled code automatically (csp.md).
- Avoid remote content such as CDN scripts (csp.md). Rust/WebAssembly frontends need `'wasm-unsafe-eval'` as a `script-src` (csp.md).
- CSP can be a string or an object of directives (e.g. `default-src`, `connect-src`, `img-src`); the example uses `ipc: http://ipc.localhost` in `connect-src` and `asset: http://asset.localhost` in `img-src` (csp.md, http-headers.md).
- `app.security.headers` (since v2.1.0): applies to responses to the webview, not IPC messages or error responses; allowed names are limited to a fixed list (CORS `Access-Control-*`, `Cross-Origin-*`, `Permissions-Policy`, `Service-Worker-Allowed`, `Timing-Allow-Origin`, `X-Content-Type-Options`, `Tauri-Custom-Header`). CSP is not set there (http-headers.md).
- Header values: string as is, array joined by `, `, key-value object joined as `key value` pairs with `; `, `null` ignores the header (http-headers.md).
- For dev mode, repeat the headers in `vite.config.ts` `server.headers`; Tauri cannot inject headers into the dev server (http-headers.md).
- Asset protocol: needs `app.security.assetProtocol.enable: true` and a `scope`; array form is allow-only, object form supports `allow`, `deny`, `requireLiteralLeadingDot` (asset-protocol.md).
- Asset scope patterns must match absolute resolved paths (use `$HOME`, `$APPCACHE`, `$RESOURCE` or a leading `/`); `["*/**"]` does not match (asset-protocol.md).
- On Unix `requireLiteralLeadingDot` defaults to true so wildcards skip dot-prefixed segments such as `.cache`; set it to `false` only in the object form and with care (asset-protocol.md).
- Prefer `**/*` over bare `**`, and narrow directories over `$HOME/**/*` or `**/*` (asset-protocol.md).
- Runtime-chosen paths (e.g. from the dialog plugin) may need the persisted-scope plugin with the `protocol-asset` feature; register `tauri_plugin_fs` before `tauri_plugin_persisted_scope` (asset-protocol.md).
- Tauri uses the OS WebView and does not bundle one, for faster security patch rollout (overview.md).
- Lifecycle: the built-in dev server has no mutual auth or encryption, so do not use it on untrusted networks (lifecycle.md). Use `npm audit` and `cargo audit`, sign binaries, pin CI actions, keep Tauri/rustc/nodejs updated (lifecycle.md).
- Report vulnerabilities privately (GitHub Vulnerability Disclosure or security@tauri.app), not publicly (overview.md).

## How to grant a plugin permission to a window with least privilege
1. Read capabilities.md and permissions.md; find the plugin's permission identifiers on its plugin page (tauri-official-plugins skill) or in the generated schema in `src-tauri/gen/schemas`.
2. Open `src-tauri/capabilities/default.json`; list the window labels (not titles) that need the permission in `windows` (capabilities.md).
3. Add the needed identifiers, e.g. `core:window:allow-set-title` or `<plugin>:allow-<command>`. `<plugin>:default` is a set of permissions; check in the plugin's permission reference what it enables and list only the `allow-*` identifiers you need (permissions.md, plugins.md).
4. If a plugin permission needs a narrower scope, define a `[[set]]` or `[[permission]]` in `src-tauri/permissions/<name>.toml` combining scope and command permissions (permissions.md, scope.md), then reference its identifier in the capability.
5. To restrict app commands per window, list them in `build.rs` via `AppManifest::new().commands(&[...])`; by default app commands are allowed for all windows (capabilities.md).

## How to set a CSP
1. Read csp.md. Set `app.security.csp` in `tauri.conf.json` (string or directive object) instead of `null`.
2. Allow only `'self'` plus the Tauri channels you need (`ipc: http://ipc.localhost`, `asset: http://asset.localhost` if using the asset protocol) and hosts you own (csp.md).
3. Verify in the running app (`pnpm tauri dev` and a built app) that Vite dev features still work; the docs do not cover Vite-specific CSP needs, so check the live page and test.

## How to expose local files to the webview
1. Read asset-protocol.md. Set `assetProtocol.enable` and a narrow object-form `scope` with `allow` (and `deny` for secrets).
2. Add `asset:` and `http://asset.localhost` to the CSP `img-src` or relevant directive (csp.md).
3. Load files in the frontend via `convertFileSrc` (asset-protocol.md).
