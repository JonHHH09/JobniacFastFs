# Tauri Plugin Development

These instructions and the files in `references/` are local copies of the official Tauri v2 docs (https://v2.tauri.app/develop/plugins/, tauri-docs 4b74da6, 2026-10-13). Work only from them: before writing code or giving advice, read the reference file(s) for the task; cite the page URL from the file's Source header. If the references don't cover something, say so and point to the live page instead of filling the gap from memory.

## Project context
- JobniacFast currently only consumes plugins (tauri-plugin-opener); its backend is in `src-tauri/`, and capabilities in `src-tauri/capabilities/default.json`.
- A plugin made in this repo must also be granted in a capability to be callable from the frontend (plugins.md).
- Package manager is pnpm; the docs only show `npx @tauri-apps/cli plugin new [name]` (plugins.md), so adapt the runner yourself and say so.
- Permission/scope concepts live in the tauri-security skill.

## Key rules
- A plugin is a Cargo crate plus an optional NPM package for API bindings; it may also include an Android library project and a Swift package for iOS (plugins.md).
- Naming: crate `tauri-plugin-{plugin-name}`, JS package `tauri-plugin-{plugin-name}-api` by default; the docs recommend a scoped name `@scope-name/plugin-{plugin-name}` (plugins.md).
- Identifier rules for the plugin name and permission identifiers: lowercase ASCII, digits, hyphens (not leading/trailing), single colon only with a prefix; underscores/uppercase are rejected and the build fails (plugins.md). permissions.md lists a different limit (see tauri-security skill); treat as unresolved doc inconsistency.
- `plugin new` flags: `--no-api` skips the NPM package, `--android` and `--ios` add mobile projects (plugins.md).
- Template layout: `src/commands.rs`, `desktop.rs`, `error.rs`, `lib.rs`, `mobile.rs`, `models.rs`, plus `permissions/`, `android`, `ios`, `guest-js`, `dist-js`, `Cargo.toml`, `package.json` (plugins.md).
- To add mobile support to an existing plugin: plugins.md says `plugin android add` and `plugin ios add`, plugins-develop-mobile.md says `plugin android init` and `plugin ios init`. The docs disagree; verify with `--help` or the live page (plugins.md, plugins-develop-mobile.md).
- Platform support is declared in `Cargo.toml` `[package.metadata.platforms.support]` with `level` (`full`/`partial`/`none`) and optional `notes` per platform (plugins.md).
- App-side plugin config lives under `plugins.<plugin-name>` in `tauri.conf.json`; define a `Deserialize` `Config` and use `Builder::<R, Config>::new("<plugin-name>")` (use `Option<Config>` to make it optional) and read it with `api.config()` in `setup` (plugins.md).
- Lifecycle hooks on `tauri::plugin::Builder`: `setup`, `on_navigation` (return `false` to cancel), `on_webview_ready`, `on_event` (RunEvent, e.g. `ExitRequested` with `api.prevent_exit()`, `Exit`), `on_drop` (plugins.md).
- Mobile lifecycle: `load` (both platforms) and `onNewIntent` (Android only) (plugins-develop-mobile.md).
- Rust APIs in `desktop.rs`/`mobile.rs` are exported as a struct named after the plugin in PascalCase and managed as state, retrieved via an extension trait on a `Manager` (e.g. `GlobalShortcutExt`) (plugins.md).
- Shared logic for desktop and mobile goes in `lib.rs` as an `impl` on the plugin struct (plugins-develop-mobile.md).
- Commands in `commands.rs` are regular Tauri commands (can take `AppHandle<R>`, `Window<R>`, `Channel`) and must be registered with `.invoke_handler(tauri::generate_handler![...])` in `lib.rs` (plugins.md).
- JS bindings call `invoke('plugin:<plugin-name>|command', args)`; build the TypeScript before testing (plugins.md).
- Commands are NOT accessible from the frontend by default (denied error); each needs a permission allowing it (plugins.md).
- Permission files are JSON or TOML in `permissions/`; a file can hold `[[permission]]`, `[[set]]` and `[default]` (plugins.md).
- `build.rs`: list command names in snake_case in `const COMMANDS` and `tauri_plugin::Builder::new(COMMANDS).build()` generates `allow-<command>` and `deny-<command>` permissions (plugins.md).
- Default permission is a set with identifier `default`; include the commands the plugin needs to be useful (plugins.md).
- A permission with no commands is a scope permission defining the global scope; read it with `tauri::ipc::GlobalScope`, and per-command scope with `tauri::ipc::CommandScope` (`allows()`/`denies()`). Check both (plugins.md).
- Scope schema: add `schemars` to both `[dependencies]` and `[build-dependencies]`, share `src/scope.rs` into `build.rs` via `#[path]`, and call `.global_scope_schema(schemars::schema_for!(...))` (plugins.md).
- Android: Kotlin class extends `app.tauri.plugin.Plugin`, annotated `@TauriPlugin`; methods annotated `@Command` take `invoke: Invoke`; args are `@InvokeArg` classes parsed with `invoke.parseArgs` (plugins-develop-mobile.md).
- Android commands run on the main thread; long work must go on a coroutine (e.g. `Dispatchers.IO`) or the UI freezes (ANR) (plugins-develop-mobile.md).
- iOS: Swift class extends `Plugin`; functions are `@objc` with `(_ invoke: Invoke)`; args are `Decodable` classes; default argument values are NOT supported (plugins-develop-mobile.md).
- Call mobile commands from Rust with `run_mobile_plugin("commandName", payload)` using camelCase-serialized payloads (plugins-develop-mobile.md).
- Mobile permissions: Android declares them in `@TauriPlugin(permissions = [...])` with aliases; iOS overrides `checkPermissions`/`requestPermissions`. Tauri provides the `checkPermissions` and `requestPermissions` commands (plugins-develop-mobile.md).
- Plugin events: `trigger(name, data)` in Kotlin/Swift, listened in JS with `addPluginListener`, which needs the plugin's permission in a capability (plugins-develop-mobile.md).
- Calling Rust from mobile code uses JNI on Android and C FFI (`@_silgen_name`) on iOS; Android 16KB pages may need a `.cargo/config.toml` rustflag with older NDKs (plugins-develop-mobile.md).

## How to scaffold a plugin and add a command
1. Read plugins.md. Run `npx @tauri-apps/cli plugin new <name>` (add `--no-api`, `--android`, `--ios` as needed).
2. Write the command in `src/commands.rs`, register it in `.invoke_handler(tauri::generate_handler![...])` in `lib.rs`.
3. Add its name (snake_case) to `COMMANDS` in `build.rs` to autogenerate `allow-<name>`/`deny-<name>`; add it to `permissions/default.toml`'s `permissions` if it should be on by default.
4. Add the JS binding in `guest-js` calling `invoke('plugin:<plugin-name>|<command>')`, then build it.
5. In the consuming app, register the plugin with `.plugin(...)` and add the permission (e.g. `<plugin-name>:default`) to `src-tauri/capabilities/default.json`.

## How to add a mobile command
1. Read plugins-develop-mobile.md. Add the Kotlin `@Command` function and/or Swift `@objc` function to the plugin class.
2. Define argument classes (`@InvokeArg` on Android, `Decodable` on iOS) and parse with `invoke.parseArgs`.
3. Call it from `mobile.rs` via `run_mobile_plugin` and expose it through `commands.rs`.
4. Keep blocking work off the Android main thread.
